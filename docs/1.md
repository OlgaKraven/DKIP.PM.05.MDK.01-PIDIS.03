# Лабораторная работа №1 - Анализ документа заказчика для разработки ИС

## **1. Теория**

### **1.1. Анализ документов заказчика**
Анализ документов заказчика — начальный этап проектирования информационной системы, направленный на понимание предметной области и требований к данным.  
На данном этапе изучаются:

- брифинг и техническое задание;
- формы документов (заказы, договоры, заявки, отчёты);
- прайс-листы, справочники;
- скриншоты интерфейсов;
- выгрузки из существующих систем (1С, CRM, Excel и т.п.).

Цель анализа — выявить:
- какие **объекты** существуют в системе;
- какие **характеристики** у этих объектов;
- какие **связи** существуют между объектами.

**Пример:**  
В брифинге интернет-магазина встречаются слова *клиент*, *заказ*, *товар*, *оплата*.  
На основе этого выделяются сущности: `Customers`, `Orders`, `Products`, `Payments`.


### **1.2. ER-диаграмма**
ER-диаграмма (Entity–Relationship Diagram) — графическая модель данных, описывающая логическую структуру базы данных.

ER-диаграмма отображает:
- сущности (таблицы);
- атрибуты сущностей;
- первичные и внешние ключи;
- связи и их кратности.

ER-диаграмма используется:
- на этапе проектирования БД;
- для согласования структуры данных с заказчиком;
- как основа для последующей реализации БД.

**Пример:**  
Сущность `Orders` связана с сущностью `Customers` отношением 1:M, так как один клиент может оформить несколько заказов.


### **1.3. Сущности и атрибуты**
**Сущность** — объект предметной области, о котором необходимо хранить информацию.  
Обычно сущности соответствуют существительным из документов заказчика.

**Атрибут** — характеристика сущности, описывающая её свойства.

**Первичный ключ (PK)**:
- однозначно идентифицирует запись;
- не может быть NULL;
- должен быть уникальным.

**Внешний ключ (FK)**:
- ссылается на PK другой сущности;
- обеспечивает связь между таблицами.

**Пример:**
- `Customers(customer_id PK, email, full_name, phone)`
- `Orders(order_id PK, customer_id FK, created_at, status)`

### **1.4. Связи между сущностями**
Связи определяют, как сущности взаимодействуют друг с другом.

Основные типы связей:
- **1:1** — одной записи соответствует одна запись;
- **1:M** — одной записи соответствует несколько записей;
- **M:N** — множественная связь, реализуемая через связующую таблицу.

Для каждой связи указываются:
- кратность;
- обязательность участия сущностей.

**Примеры:**
- `Customers → Orders` — связь 1:M (один клиент — много заказов);
- `Orders → Payments` — связь 1:M;
- `Orders ↔ Products` — связь M:N, реализуется через `Order_Items`.


### **1.5. Нормализация данных**
Нормализация — процесс упорядочивания структуры базы данных для:
- устранения избыточности;
- предотвращения аномалий вставки, обновления и удаления;
- повышения целостности данных.

Проектирование ER-диаграммы должно завершаться приведением модели к 3-й нормальной форме (3НФ).


### **1.6. Первая нормальная форма (1НФ)**
Таблица находится в 1НФ, если:
- все атрибуты атомарны;
- отсутствуют повторяющиеся группы.

**Нарушение 1НФ:**
- поле `phones = "8-900..., 8-901..."`

**Исправление:**
- вынос номеров телефонов в отдельную таблицу `Customer_Phones`.


### **1.7. Вторая нормальная форма (2НФ)**
Таблица находится во 2НФ, если:
- она находится в 1НФ;
- все неключевые атрибуты зависят от всего первичного ключа.

Актуально для таблиц с составным PK.

**Нарушение 2НФ:**
- `Order_Items(order_id, product_id, product_name)`

`product_name` зависит только от `product_id`.

**Исправление:**
- `product_name` переносится в таблицу `Products`.


### **1.8. Третья нормальная форма (3НФ)**
Таблица находится в 3НФ, если:
- она находится во 2НФ;
- отсутствуют транзитивные зависимости.

**Нарушение 3НФ:**
- `Orders(order_id, customer_id, customer_name)`

`customer_name` зависит от `customer_id`, а не от PK напрямую.

**Исправление:**
- `customer_name` хранится в `Customers`.


### **1.9. Ссылочная целостность**
Ссылочная целостность обеспечивает корректность связей между таблицами базы данных.

Правила ссылочной целостности:
- каждый FK указывает на существующий PK или UNQ;
- нельзя удалить запись, на которую существуют ссылки, без согласованной логики;
- обязательность связей должна быть логически обоснована.

**Пример:**
- `Orders.customer_id` ссылается на `Customers.customer_id`;
- удаление клиента запрещено при наличии заказов (`RESTRICT`).

## **2. Задание**

### **2.1. Анализ предметной области**
1) Изучить брифинг и документы заказчика.  
2) Выделить основные сущности предметной области.  
3) Зафиксировать допущения при отсутствии информации.

### **2.2. Проектирование ER-диаграммы**
1) Определить первичные и внешние ключи для всех сущностей.  
2) Установить связи между сущностями с указанием кратностей.  
3) Реализовать связи M:N через связующие таблицы.  
4) Привести модель к 3-й нормальной форме.

### **2.3. Оформление результата**
1) Подготовить ER-диаграмму в нотации ER (Crow’s Foot / Chen) или UML Class Diagram.  
2) Экспортировать итоговую диаграмму в формат PDF.  

### **2.5. Для выполнения требуется**

1. **Шаблон отчёта**, указанный в описании лабораторной работы.
2. **Вариант задания**, закреплённый за студентом на семестр и опубликованный в ЛМС.
3. **Требования к оформлению** — согласно методическим указаниям в ЛМС или соответствующему разделу документации.
4. Для построения диаграмм использовать **draw.io (diagrams.net)**.
